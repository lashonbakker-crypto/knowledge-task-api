# 面试准备与简历表述

当前仓库首版由 AI 辅助创建。两年后能否写进简历，取决于你后续真正理解、修改、验证和使用了哪些部分。项目名称与代码体积不能替代这些经历。

## 应能当场解释

1. 为什么保存任务到数据库，而不是仅使用 FastAPI 的临时后台函数？进程退出后两者有什么区别？
2. 同时收到两个相同请求，唯一约束和事务分别解决什么？不同内容复用同一 key 怎样处理？
3. 为什么仅检查 `state=running` 不够？旧 worker 过期后为何还可能继续计算？
4. 取消与完成同时发生时，哪个操作先得到写锁会产生什么结果？
5. 文档入库成功但 FTS 索引失败时，数据库里应留下什么？如何证明？
6. “至少一次执行”和“至多一次结果发布”有什么区别？外部工具副作用为何需要单独设计？
7. SSE 断线后怎样恢复？为什么游标要限制整数范围？
8. 只在 API 层隐藏 ID 能否隔离数据？为什么 Store 查询仍带租户条件？
9. SQLite WAL 的好处与写入限制是什么？迁移 PostgreSQL 时哪些测试不能删？
10. 如何证明优化有效？如何避免把本机测试数值称为生产吞吐？

建议演示一次正常入库，再现场改一行去掉 fencing 检查，预测并运行对应测试，最后解释修复。这个过程比记住接口名更有说服力。

## 简历模板：满足条件后再使用

如果你已亲自维护并完成了对应实现，可写：

> 知识检索与任务平台后端（个人项目）：基于 FastAPI 与关系数据库实现异步文档入库和检索接口；设计幂等请求、有限重试、租约 fencing 与事件回放，覆盖并发请求、旧 worker 写回、取消和崩溃恢复等回归场景；负责【你实际实现的模块】与【你实际做过的实验】。

完成 PostgreSQL 或 Agent 接入后，再准确替换技术栈和增加相应功能。写性能数字前，需要保存硬件、数据量、负载、前后版本、测量脚本和原始结果；没有这些记录时，用具体行为与验证描述，不填想象的提升百分比。

面试中如实说明 AI 的参与，展示你自己的决策、改动与反例验证。避免把首版宣传为上线生产、大规模分布式系统或已经具备完整 Agent 能力。
