# 为什么“流结束了”也可能漏掉最后一条消息？

本项目用 SSE 把任务事件持续发送给客户端。SSE 可以理解为一条暂时保持连接的 HTTP 响应：服务端每产生一条消息，就向客户端发送一段文字。这里的消息来自数据库，包含排队、开始执行、成功、失败或取消。

## 本轮真实问题

旧代码先查事件，再查任务是否结束。这两次查询之间，worker 可能完成任务。

| 时刻 | 数据库或服务端发生什么 | 客户端得到什么 |
| --- | --- | --- |
| 1 | 查询事件，暂时只有 ID 1 的 queued 和 ID 2 的 running | 两条已有事件 |
| 2 | worker 在同一事务里写入 succeeded 状态和 ID 3 的成功事件 | 此时还没读取 ID 3 |
| 3 | 查询任务，看到 succeeded | 服务端认为可以关流 |
| 4 | 发送 end 并关闭 | 漏掉 ID 3，包括成功结果的文档 ID |

数据库里没有丢数据，客户端却没收到最后一条。这叫竞态：结果依赖两个操作之间另一个任务插入执行的时机。首次连接和从游标续读都可能发生；失败或取消也一样。

## 修复为什么成立

现在每轮先查询任务状态，再查询这一轮的事件。

1. 如果第一步已经看到终态（succeeded / failed / cancelled），同一个数据库事务里的终态事件也已经提交。随后按游标读取，可以把它发送出去。
2. 如果第一步还看到 running，随后任务结束，这一轮不凭后来出现的终态提前关流；下一轮再读取。事件可能这一轮就读到，也可能下一轮才读到。
3. 每页最多 100 条。收到满页时继续读；确认当前任务已经结束，并读到不满的一页后，才发送 end。测试覆盖了 201 条事件，不能只发第一页。

这依赖 [Store](../knowledge_task_api/store.py) 把状态和事件放在同一事务提交，并且终态之后不再追加新的任务状态事件。它没有把所有读取变成一个原子快照，也没有保证客户端网络永远不断开。连接超时或断开后，仍要带最后收到的事件 ID 重连。

## 三个词

| 词 | 在这里是什么意思 |
| --- | --- |
| 事务 | 几次数据库写入一起成功，或一起回滚。任务成功状态与成功事件不会只保存一个 |
| 游标 | 记住最后已收到的事件 ID；下次读取 ID 大于它的消息 |
| 终态 | 一个任务已经成功、失败或取消，不再正常继续执行 |

## 5–10 分钟练习

先按 README 建好虚拟环境并安装测试依赖，再执行：

```bash
python -m pytest tests/test_api.py -k 'finishes_during_poll or drains_multiple' -v
```

应该看到 7 个场景通过：成功 / 失败 / 取消各包含首次连接和游标续读，再加一个 201 条事件分页场景。测试使用真实 SQLite；在一次事件查询取得结果后提交真实终态事务，精确复现竞态，不靠随机 sleep 猜时机。

然后打开 [事件流接口](../knowledge_task_api/api.py)，找到内部的 `emit()`，看 `get_task` 与 `task_events` 的先后顺序；再读 [回归测试](../tests/test_api.py) 的 `read_then_finish()`。试着用上面的四行表解释：为什么两行读取代码交换顺序，就能避免提前关闭？

面试时可以描述项目中的这个案例：**“我复现了 SSE 在状态变化时漏发终态事件的问题，利用状态与事件在同一事务提交的约束调整读取顺序，并验证了游标续读和多页事件。”** 只有在自己跑过并能解释之后，才把它表述为自己掌握的经历。
